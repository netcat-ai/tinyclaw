执行摘要

msghub 的核心判断是：终端 agent 和 AI agent 的协议动作可以统一，但它们的角色语义不能混在同一个业务分支里。统一接口，分离 Actor Kind，是当前最小且可扩展的设计。

3个 HTTP endpoint

只暴露 /ilink/sendmessage、/ilink/getupdates、/ilink/ack。

7张核心表

Actors、Rooms、Messages、Subscriptions、Inbox、Tasks、Capability Tokens。

1套 iLink-like 协议

terminal-agent 与 aiagent 共享同一套拉取、发送、确认模型。

当前状态：内存 store、Postgres store、进程级 HTTP e2e 和 DB 数据检查均已通过。msghub 使用独立数据库，不修改现有 Clawman 表。

背景与边界

现有 Clawman 是 Room-scoped agent runtime control plane。它的核心对象是 Room、Message、Agent Session、Agent、Room Memory 和 Delivery。它负责触发 Agent Run、调用 Codex、写 Memory、产出 Delivery。

msghub 则是 mailbox-shaped actor broker。它不负责 AI 运行时，不拥有 prompt，不管理 memory，也不持有 Codex thread。它只处理协议客户端之间的消息事实、订阅投递和任务分派。

维度 Clawman Core Model msghub Actor Broker
系统职责 Agent Runtime Control Plane Message Hub / Actor Broker
Room 语义 带 Agent Session、trigger policy、memory 的运行空间 外部会话身份和消息时间线
Outbound deliveries，由 Agent Run 产出 actor_tasks，分派给 Actor 执行
协议入口 /api/rooms、/api/messages、/api/deliveries /ilink/sendmessage、/ilink/getupdates、/ilink/ack
数据库 现有 TinyClaw DB 独立 msghub DB

这意味着 msghub 不是对 Clawman 的兼容层，也不是 Clawman 表结构的迁移版本。它复用的是思想：Room 作为消息载体、Message 作为 append-only fact、Delivery 思路演化为 Actor Task、token 表思路演化为 scoped capability。

领域模型

v0 的领域模型故意保持小。它只保留消息中心必须知道的事实，不引入 agent runtime 的状态字段。

对象 定义 关键规则
Actor 协议客户端，可以是 terminal、aiagent、admin。 Actor 不是微信里的消息发送人；它是连接 msghub 的系统身份。
Room 外部会话载体，私聊和群聊都映射成 Room。 每条 Message 必须属于一个 Room。
Message append-only 原始消息事实。 幂等键是 room_id + source_actor_id + external_message_id。
Actor Subscription Actor 订阅哪些 Room 的消息事件。 terminal 不需要订阅 Room 才能收到分派任务。
Actor Inbox 每个 Actor 的收件箱。 记录投递状态，不记录任务业务结果。
Actor Task 分派给某个 Actor 执行的任务。 v0 第一种任务是 send_message。
Capability Token 短期、带范围的操作授权。 reply token 允许 aiagent 基于收到的消息创建回复任务。
v0 明确不引入 direction、raw_payload、agent_session_id、source_message_from_id、source_message_to_id。这些字段属于旧模型或运行时边界，不属于独立消息中心的最小核心。

协议与数据流

对外协议只有一套 iLink-like HTTP 接口。sendmessage 的语义由 Actor Kind 决定：terminal 调用表示上报外部真实消息；aiagent 调用表示基于上下文授权创建发送任务。

Endpoint 语义

Endpoint terminal actor aiagent actor
POST /ilink/sendmessage 上报 provider 侧收到的真实消息，写入 messages。 使用 context_token 创建 send_message Actor Task。
POST /ilink/getupdates 拉取分派给自己的任务，例如发送微信消息。 拉取订阅到的消息和任务执行结果。
POST /ilink/ack 确认 inbox item，并提交 task 成功或失败。 确认自己已经处理过的 inbox item。

模块与调用者

当前实现把 HTTP、领域模型、内存 store、Postgres store 和进程入口分开。Store interface 是最重要的内部边界：server 不关心数据落在内存还是 Postgres。

模块 职责 调用方向
cmd/msghub/main.go 进程入口，读取环境变量，选择 store，seed 默认 Actor，启动 HTTP server。 调用 internal/msghub。
internal/msghub/server.go HTTP 协议边界，认证 Bearer token，按 Actor Kind 分发 sendmessage。 依赖 Store interface。
internal/msghub/model.go 领域对象、事件类型、请求响应 DTO。 被 server/store/test 共用。
internal/msghub/postgres_store.go Postgres 事务、幂等写入、fanout、task 状态、capability 校验。 实现 Store。
internal/msghub/memory_store.go 内存实现，用于快速测试和无 DB 临时启动。 实现 Store。
internal/msghub/schema.sql 独立 msghub schema。 由 Postgres store embed 并初始化。

外部调用者

terminal

Linux WeChat Agent

在 Linux 容器里连接微信客户端。它把微信收到的消息同步到 msghub，也从 msghub 拉取发送任务并调用微信客户端发送。

aiagent

Clawman-as-agent

未来 Clawman 可以作为 aiagent actor 接入。它从 msghub 拉取消息，再把回复意图写回 msghub。

admin

Management Client

概念已保留，但 v0 暂无 admin API。Actor seed 当前通过环境变量完成。

数据库设计

DB 设计遵循一个原则：消息事实、投递状态、执行任务分开存。不要用一张 messages 表同时表达事实、订阅者进度和待执行命令。

表 目的 关键约束
actors 协议客户端身份。 actor_key unique，token_hash unique，kind 限定为 terminal、aiagent、admin。
rooms 外部会话身份。 tenant_id + channel + provider_account_id + external_room_id unique。
messages append-only 消息事实。 room_id + source_actor_id + external_message_id unique。
actor_subscriptions Actor 对 Room 的订阅关系。 actor_id + room_id unique。
actor_inbox 每个 Actor 的收件箱投递状态。 actor_id + event_type + resource_type + resource_id unique。
actor_tasks 分派给 Actor 执行的任务。 status 限定为 pending、acked、failed。
capability_tokens 短期授权。 action 限定为 reply、send_message、ack_task；uses_remaining 不能小于 0。

明确不保留的兼容字段

direction
raw_payload
agent_session_id
source_message_from_id
source_message_to_id
prompt
memory_items
memory_write_jobs
memory_change_audit

这些字段不进入 msghub v0，是因为它们要么属于旧 Clawman runtime，要么会把 provider 原始数据和规范化消息事实重新混在一起。v0 把 provider-specific detail 放进 messages.body 或 actor_tasks.payload。

剩余决策

v0 已经能支撑 terminal-agent 与 aiagent 通过统一接口完成消息收发闭环。下一层真正需要决策的是生产可运维能力，而不是继续加字段。

主题 当前判断 触发条件
Actor 管理 API v0 用环境变量 seed 足够。 需要动态创建 terminal/aiagent、禁用 Actor、轮换 token。
Capability Token 存储 当前存明文 token 以支持 getupdates 重放同一个 pending inbox。 进入生产安全审计时，改为签名自包含 token 或加密存储。
Room Participants v0 不需要。 需要完整群成员列表、成员角色、当前 display name、跨 Room 身份合并。
Media Objects v0 放在 body/payload。 需要预上传、复用、过期、加密 CDN 元数据或 scoped media URL。
Task Retry / Lock v0 只记录 pending、acked、failed。 terminal-agent 多实例、任务超时重试、死信队列。
Clawman 接入 应作为 aiagent actor 接入。 需要把当前 /api/messages -> Agent Run -> Delivery 改成 /ilink/getupdates -> Agent Run -> /ilink/sendmessage。

推荐下一步不是继续扩表，而是实现一个最小 Linux WeChat terminal-agent，用真实微信客户端完成：读取消息、写入 msghub、拉取 send_message task、发送微信、ack task。
